# 代码共性组件抽取：`_edits` 结果总结

## 1. 实验范围

本报告基于以下已完成评估的结果：

- CodeContests：`demo/results/codecontest_edits/`
- Scrapy complex：`demo/results/complex_edits/`
- CodeContests signal 方法：`demo/results/codecontest_edits/signal/`（工具信号 + LLM 判定门发现，本轮仅跑 CodeContests，未跑 Scrapy）

所有方法使用相同的评估口径：`compare_mode=original`、空白归一化、每个文件使用全部可用测试。CodeContests 使用 stdio 测试，Scrapy complex 使用 pytest。MDL 使用 `Qwen3.8-27B-Q4_K_M.gguf`；冲突率对当前 edit-intent 输出不适用，因此显示为 `not_available`。

完整的逐 cluster/subcluster 表格见 [report_edits.md](report_edits.md)。

## 3. 生成与测试结果

### 3.1 CodeContests

baseline-a 的 10 个 cluster 全部生成成功，300 个改写文件均已落盘并通过编译。原始代码通过测试的 280 个有效文件中，改写版全部通过；对应 24,956 个有效测试也全部通过。

baseline-b 发现了 73 个有效子簇，生成 237 个成员文件；59 个子簇测试完整通过，14 个子簇存在行为退化。加权 file pass rate 为 91.5%，test pass rate 为 95.6%。因此，baseline-b 的子簇划分和局部抽取虽然提高了复用覆盖，但整体功能稳定性低于 baseline-a。

signal 方法的工具信号层（逐字克隆 / AST 骨架 / 语义 embedding）在 10 个 cluster 上产生 59 个候选簇，覆盖 181/300 个文件——这个"粗召回"数量与 baseline-b 的 73 个子簇同量级。LLM 判定门随后拒绝了 36 个弱候选，并对其余候选剔除低置信成员（多数收窄为 2 文件的高置信对），最终得到 24 个有效子簇、53 个成员文件，全部编译通过，53 个有效文件与全部有效测试 100% 通过。signal 的判定门相当于把 baseline-b 放在抽取阶段承担的功能退化风险前移到了发现阶段提前过滤。

### 3.2 Scrapy complex

baseline-a 对 24 个文件全部生成并通过编译；23 个原始有效文件和 711 个有效测试全部匹配。

baseline-b 发现 6 个有效子簇，生成 20 个成员文件，其中 5 个子簇完整通过，`sub_0` 未完全通过。总体 file pass rate 为 94.7%，test pass rate 为 96.4%。另有 4 个文件被发现阶段判定为噪声，未进入 baseline-b 改写。

## 4. 压缩与复用分析

### 4.1 CodeContests

baseline-a 的 token 总量从 121,644 降至 116,751，整体 token 压缩为 4.0%；但 MDL 从 83,278.17 增至 83,517.04，MDL 压缩为 -0.29%。这说明改写在功能上稳定，但加入 `common.py` 后信息量并未稳定下降。

baseline-b 的 token 总量从 108,391 降至 96,719，token 压缩为 10.8%；MDL 压缩为 0.83%。不过该结果建立在子簇成员范围口径上，且 14 个子簇测试失败，因此不能把全部压缩都视为有效收益。只有同时满足功能通过和真实 API 复用的子簇，才适合作为正向案例。拆开看，59 个通过的子簇 token 压缩为 10.2%（84,299 → 75,726）、MDL 为 -0.24%，而 14 个失败的子簇 token 压缩反而更高（12.9%）并贡献了几乎全部的正 MDL——即 baseline-b 报告口径中的正收益主要由行为退化的子簇提供，这与功能测试结论相互印证。

signal 在覆盖成员口径上的 token 压缩为 11.4%（24,407 → 21,635），与 baseline-b 的 10.8% 相当，且没有失败子簇稀释；MDL 压缩为 +0.68%（覆盖子簇 Σ 口径）。但 signal 的有效子簇只覆盖 53/300 个文件（约语料 token 的 20%），未改写文件不产生收益，按全语料口径把每个方法视为对 300 个文件的一次压缩、失败子簇计零收益，三方法为：baseline-b -7.05%（121,644 → 113,071）、baseline-a -4.02%、signal -2.28%（121,644 → 118,872）。signal 的总量最小是覆盖范围窄的结果，而非单点抽取效率低。

### 4.2 Scrapy complex

baseline-a 的 token 变化几乎为零（-0.005%），MDL 为 -0.49%，说明端到端方法在框架代码上采取了保守改写。

baseline-b 的 token 压缩为 -3.7%，MDL 压缩为 -7.06%，即加入公共组件和 import 后总体代码信息量反而增加。框架代码的共性主要体现在继承、生命周期和回调协议上，单纯抽取少量 helper 很难抵消公共模块和改写接口的开销。

## 5. 方法结论

1. **功能稳定性：baseline-a 更好。** 两个数据集上 baseline-a 都达到 100% 的有效 file/test pass；baseline-b 分别为 91.5%/95.6% 和 94.7%/96.4%。
2. **算法题上的 baseline-b 有局部压缩收益。** 先发现再抽取能够提高成员文件的 API 覆盖率，但发现错误或子簇内部接口不一致时，会引入功能退化。
3. **框架代码上的抽取收益不足。** Scrapy complex 的两个方法都没有获得稳定的 token 或 MDL 压缩；baseline-b 的压缩还明显为负。
4. **API 覆盖不等于有效抽取。** CodeContests baseline-b 的文件 API 覆盖达到 92.0%，但仍有 14 个子簇测试失败。功能测试应当优先于压缩率和复用覆盖率。
5. **baseline-b 的噪声策略影响覆盖范围。** 被发现阶段判定为噪声的文件保持原样，不应与已改写成员混入同一功能分母解读。
6. **signal 是零失败的高置信抽取方案。** 24/24 子簇功能通过，覆盖成员 token 压缩 11.4% 与 baseline-b 相当、MDL 0.68% 为正；代价是覆盖仅 53/300 个文件，全语料压缩 -2.28%，低于 baseline-a 与 baseline-b。
7. **"粗召回"在工具层已经实现，真正的取舍点是判定门。** signal 的工具信号层产出 59 个候选簇、覆盖 60% 的文件，与 baseline-b 的 73 个子簇同量级；LLM 判定门拒绝弱候选，等于把 baseline-b 在抽取后承担的失败风险前移到发现阶段。因此 signal 数量少不是发现失灵，而是拒绝了自己没有把握的候选。
8. **signal 与 baseline-b 对"可安全抽取"的判断高度一致。** 对 CodeContests 的结果做事后交叉比对：signal 的 24 个有效簇中有 19 个是 baseline-b 某簇的子集，4 个为 signal 独立发现（其中 3 个在 cluster 8）。两套独立方法（工具证据 + LLM 门 vs 纯 LLM 发现）认定的可抽取共性几乎重合，差异只在于 baseline-b 通过承担 19% 的子簇失败风险把覆盖从 53 个文件扩大到 237 个文件。

## 6. 失败项

本次评估阶段的失败不是“没有生成代码”，而是已生成并编译的改写代码未通过全部行为测试：

- CodeContests baseline-b：`0/sub_3`、`0/sub_4`、`0/sub_6`、`1/sub_0`、`2/sub_0`、`2/sub_3`、`3/sub_1`、`4/sub_4`、`6/sub_2`、`6/sub_7`、`6/sub_8`、`9/sub_2`、`9/sub_3`、`9/sub_5`
- Scrapy complex baseline-b：`0/sub_0`

详细测试结果、token/MDL 文件和每个单元的状态分别保存在对应的 `metrics.json`、`mdl_metrics.json` 和 `status.json` 中。signal 方法本轮无失败项（24/24 子簇 ok）。

## 7. 最终结论

在当前数据和评测口径下，三种方法构成"覆盖率 ↔ 风险"的连续谱：

- **baseline-a 是最可靠的全覆盖默认。** 两个数据集上均保持 100% 有效测试通过，但只做整簇粗抽取，token 压缩（4.0%）低于细粒度方法。
- **baseline-b 在承担风险时取得最大收益。** 它以 14/73（19%）子簇行为退化为代价把覆盖扩大到 237 个文件，全语料 token 压缩 -7.05% 为三者最高；但报告口径中的正 MDL 收益几乎全部来自这些失败子簇。若严格采用"功能不等价的压缩不计收益"的口径，它仍领先但优势收窄。
- **signal 是保守的高置信方案。** 判定门把失败风险前移并全部滤除，24/24 零失败、覆盖成员压缩 11.4% 与 baseline-b 相当；代价是覆盖仅 53/300 个文件，全语料压缩 -2.28% 为三者最低。它与 baseline-b 的发现结果高度重合（24 簇中 19 簇是 b 簇子集、4 簇独立），印证了两方法对"可安全抽取"的判断一致，差距本质上是风险偏好。

实践含义：若只有一种默认方案，baseline-a 最稳；若要压缩收益，baseline-b 需要配套失败子簇回退机制（发现结果去重、接口一致性检查、按测试结果回滚）；signal 适合作为只接受高置信复用的下限基线，也可用作 baseline-b 的失败子簇回退替代。对于 Scrapy 这类以继承与框架回调为主要共性的代码，仅依靠当前 helper 抽取策略不能证明存在稳定的经济收益。
