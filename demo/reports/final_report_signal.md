# 基于多信号发现的代码共性组件抽取：Signal 与端到端 Baseline A 的对比研究

> 数据：Apache Libcloud 真实生产代码与 CodeContests 受控竞赛代码
>
> 模型：DeepSeek Flash API（temperature = 0）
> 核心指标：功能等价优先；仅对通过行为验证且具有正净收益的改写计入最终压缩

---

## 摘要

本文比较两种代码共性组件抽取方法：Baseline A 将整个文件簇一次性交给大模型完成共性发现、公共组件生成和成员改写；Signal 则先利用逐字克隆、AST 骨架和语义嵌入召回局部候选，再通过 LLM 判定门过滤弱候选，最后仅对高置信候选执行抽取。

实验覆盖一个真实生产代码数据集和一个受控竞赛代码数据集。在 Apache Libcloud 的 10 个 load-balancer driver 上，Signal 将完整代码池从 26,045 token 压缩到 23,471，压缩率为 **9.88%**；Baseline A 仅压缩 **0.05%**。在 CodeContests 的 300 个 Python solution 上，对双方统一采用“编译通过、行为测试全部通过且净 token 收益为正，否则回滚”的验收规则后，Signal 的完整池压缩率为 **5.13%**，Baseline A 为 **3.81%**，两者均保持 24,897 / 24,897 个有效测试通过。

结果表明，Signal 的主要优势不是无条件生成更多公共代码，而是识别异质代码池中稀疏、局部且高置信的复用关系，并让无收益或高风险文件保持原样。该优势在真实的异质目录中最明显，在结构更规整的受控数据上仍然存在，但幅度较小。

## 1 任务设定

### 1.1 任务定义

给定若干独立源代码文件组成的文件池 `C = {f_1, ..., f_n}`，目标是抽取一个或多个共享组件，并将相关成员文件改写为调用共享实现。一个有效结果必须同时满足：

1. **功能等价**：改写代码在外部测试上与原始代码行为一致；
2. **真实复用**：成员文件实际导入或调用生成的公共组件；
3. **净压缩收益**：公共组件和改写文件必须一起计入，整体 token 数少于原代码；
4. **完整池核算**：未抽取文件按原始大小保留，不能通过忽略困难文件虚增压缩率。

功能等价是硬约束。测试失败的改写即使体积更小，也不作为有效压缩结果。

### 1.2 输入隔离

CodeContests 的模型输入只包含中性化的 `file_id` 和源码。题名、题面、算法摘要、难度和 public/private/generated 测试均不进入 prompt。Libcloud 同样只向模型提供匿名化后的上游源码；仓库身份、测试和人工选择依据不作为抽取提示。

### 1.3 研究问题

- **RQ1：** Signal 能否在保持行为等价的前提下获得高于 Baseline A 的完整池压缩？
- **RQ2：** Signal 的优势是否能同时出现在真实生产代码和受控代码上？
- **RQ3：** 多信号召回与 LLM 判定门分别解决了什么问题？
- **RQ4：** 正收益筛选与失败回滚是否会造成不公平比较？

## 2 方法

### 2.1 Baseline A：整簇端到端抽取

Baseline A 将一个完整文件簇交给 LLM，由模型在一次任务中发现共性、生成 `common.py` 并改写成员文件。其优点是流程简单且能够看到完整上下文；局限是当目录内只有少数文件真正相关时，大量异质代码会稀释局部重复信号，使模型倾向于只抽取非常保守的小型 helper。

### 2.2 Signal：证据驱动的局部抽取

Signal 将发现和抽取拆开：

1. 对源码解析出函数、方法和类等代码单元；
2. 分别计算逐字克隆、AST 骨架相似和语义嵌入相似信号；
3. 融合跨文件证据并召回候选，语义通道使用 `or_top_frac = 0.005`；
4. LLM 判定门检查候选是否具有真实共享概念、可兼容接口和安全抽取边界；
5. 只对通过判定门的候选生成公共组件和局部改写；
6. 编译、运行行为测试并计算净 token 收益，不满足验收条件的候选回滚。

该流程允许一个目录产生多个局部公共组件，同时让无关文件保持不变。Signal 的核心假设是：真实代码中的共性通常是稀疏的，正确的抽取边界往往小于目录或人工文件簇。

### 2.3 统一验收与冲突处理

最终结果采用如下可执行策略：

- 编译失败、行为测试未全部通过或净 token 收益不为正的候选不应用；
- 多个候选包含同一源文件时，不允许重复计算该文件；
- 在互不重叠的可用候选中选择总 token 收益最大的组合；
- 未选择的文件保持原样，其 token 和测试均计入完整池。

相同的通过与正收益规则也应用于 Baseline A。区别只在方法原生的生成粒度：Baseline A 每个输入簇产生一个整体候选，Signal 产生局部候选。

## 3 实验设置

### 3.1 Apache Libcloud：真实生产代码

数据来自 `apache/libcloud` v3.9.1（commit `6c867a3ca299f1b16057fab96bff65564c0ac5fe`），使用 `libcloud/loadbalancer/drivers` 中除 `__init__.py` 外的全部 10 个生产模块：

- 7,440 行源码；
- 26,045 个可执行 Python token；
- 11 个上游 pytest 模块；
- 原始代码通过全部 416 个收集到的测试。

该目录同时包含多种云厂商实现。部分 provider driver 具有明确演化关系，但大多数文件彼此异质，适合验证方法能否从真实目录中定位稀疏共性。

### 3.2 CodeContests：受控竞赛代码

CodeContests 包含 10 个代码簇，每簇 30 个 Python solution：

- 共 300 个文件；
- 29,966 个 public、private 和 generated 候选测试；
- 难度字段范围为 7–22；
- 测试采用 stdin/stdout 执行并进行空白归一化比较。

CodeContests 中的代码来自竞赛解答，但不属于持续维护的生产项目。它在本研究中用于验证结构规整、重复算法模式明显时的方法表现，是受控补充证据，而非真实软件工程证据。

### 3.3 模型与执行参数

两种方法均使用 `deepseek-flash`，temperature 为 0。CodeContests 的 Baseline A cluster 调用和 Signal 的 gate/extraction 调用均使用 4 个并发 worker；最大输出长度为 65,536 token，单测试进程超时为 10 秒。Signal 的语义召回模型为本地 `C2LLM-0.5B`。

token 使用 Python tokenizer 统计，并排除注释和 docstring。当前重算未启用稳定的 logprob 参照模型，因此正文不报告 MDL，避免将不可比指标混入结论。

### 3.4 测试与压缩口径

行为比较只统计原始程序本身能够正确完成的测试。CodeContests 的 29,966 个候选测试中共有 24,897 个进入有效分母；原始程序失败、超时或不满足期望输出的测试不用于判断改写退化。

完整池压缩定义为：

```text
compression = 1 - tokens_after / tokens_before
```

其中 `tokens_after` 包含所有公共组件、所有被改写文件以及保持原样的未选择文件。

## 4 实验结果

### 4.1 统一验收后的主结果

| 数据集 | 方法 | 有效行为验证 | tokens before | tokens after | token 节省 | 压缩率 |
|---|---|---:|---:|---:|---:|---:|
| Apache Libcloud | Baseline A | 416 / 416 | 26,045 | 26,031 | 14 | 0.05% |
| Apache Libcloud | Signal | 改写范围 163 / 163；其余文件不变 | 26,045 | **23,471** | **2,574** | **9.88%** |
| CodeContests | Baseline A | 24,897 / 24,897 | 121,644 | 117,004 | 4,640 | 3.81% |
| CodeContests | Signal | 24,897 / 24,897 | 121,644 | **115,399** | **6,245** | **5.13%** |

在 Libcloud 上，Signal 的最终代码池比 Baseline A 少 2,560 token，压缩率高 9.83 个百分点。在 CodeContests 上，Signal 比 Baseline A 多节省 1,605 token，压缩率高 1.32 个百分点。两组数据在统一验收后的行为验证中均没有引入已知退化。

### 4.2 未筛选输出与回滚影响

CodeContests 的 Signal 流水线共产生 72 个抽取候选，其中 71 个通过行为测试、1 个出现性能超时。71 个通过候选中，58 个具有正 token 收益、1 个收益为零、12 个为负收益。负收益主要来自较小的重复片段不足以抵消 `common.py`、import 和包装代码的固定开销。

若把 71 个测试通过候选分别独立统计，其 token 压缩为 3.32%；但候选之间会重复包含同一源文件，因此这个数字只用于诊断，不能与完整池 Baseline A 直接比较。最终完整池结果从测试通过且正收益的候选中选取文件互不重叠的组合，共接受 29 个候选，其他文件原样保留。

Baseline A 未回滚时从 121,644 压缩到 116,417，表面压缩率为 4.30%，但 cluster 8 的改写在一个有效测试上超时。应用相同的行为验收规则后，该 cluster 整体回滚，最终压缩率为 3.81%。因此主表没有让 Signal 单方面享有失败回滚权。

### 4.3 Signal 的发现与判定门作用

Libcloud 的语义召回共处理 400 个代码单元和 68,163 个跨文件单元对。在重点 provider 演化对的 47 个同名方法中，42 个的余弦相似度不低于 0.88，召回率为 89.36%。融合阶段产生 16 个候选，LLM 判定门最终接受 2 个高置信 provider family 并拒绝其余 14 个弱候选。

这说明 Signal 的收益来自两个互补步骤：工具信号负责提高召回并找出隐藏在大型文件中的局部对应关系；LLM 判定门负责排除只有表面语义相似、但缺乏稳定共享接口的候选。若只有嵌入召回，候选噪声过多；若直接让 LLM 阅读整个异质目录，局部强重复又容易被上下文淹没。

## 5 分析

### 5.1 为什么 Signal 在真实代码上优势更大

Libcloud 的重复并不均匀分布在 10 个 driver 中，而是集中在少数具有继承或演化关系的 provider family。Baseline A 必须在同一次整簇任务中兼顾所有厂商实现，因此只抽取了少量通用 helper，最终节省 14 token。Signal 先定位相关 family，再在局部上下文中抽取共享基类，既获得更大的复用范围，也避免修改无关 driver。

这正是 Signal 最可能占优的场景：目录整体异质，但局部存在结构和语义均高度一致的实现家族；共享边界是类或方法集合，而不是整个目录。

### 5.2 为什么 CodeContests 的优势较小

CodeContests 已按算法描述聚类，同一簇中的文件比真实项目目录更规整，因此 Baseline A 也能发现一部分共享 helper。Signal 仍通过细粒度候选和回滚避免了小片段抽取造成的代码膨胀，但相对优势缩小到 1.32 个百分点。

这一结果适合作为受控条件下的补充验证：当 Baseline A 已经拥有较好的整簇输入时，Signal 仍能利用更精细的抽取边界获得增益；但它不能替代真实项目数据对工程有效性的证明。

### 5.3 负收益不是异常，而是抽取决策的一部分

公共组件抽取存在固定成本。即使两个文件包含相似代码，抽取后的公共模块、导入语句、适配参数和包装函数也可能使总代码量增加。因此“发现共性”和“值得抽取”是两个不同判断：前者要求语义或结构对应，后者还要求功能安全和经济收益。

Signal 将净收益检查作为验收门，使负收益候选回退为原文件。这样得到的是一种可部署策略，而不是对所有模型输出的无条件平均。报告同时披露 12 个负收益候选和独立候选的 3.32% 诊断值，以避免只展示正向样本。

### 5.4 公平性讨论

当前比较对双方使用相同的三个接受条件：编译成功、有效测试全部通过、净 token 收益为正。Baseline A 的候选粒度是完整 cluster，Signal 的候选粒度是发现出的局部组件；这种粒度差异是两种方法设计的一部分，也是 Signal 风险隔离能力的来源。

不过，CodeContests 的统一验收分析是在完整实验完成后确定并汇总的，不等同于预注册实验。严格的后续研究应在运行前固定选择规则，并将“用于候选验收的测试”和“最终报告的测试”分开。否则，使用同一批测试进行回滚和最终评估会带来一定的 test-set selection 偏差。

## 6 有效性威胁与局限

1. **数据规模有限。** 真实代码证据目前只有 Libcloud 的一个目标目录，能够证明存在适用场景，但不足以证明 Signal 在任意仓库上普遍优于 Baseline A。
2. **数据集选择具有针对性。** Libcloud 是通过重复结构筛选得到的强候选，因此结果属于存在性证明。未来需要在预先固定的多仓库样本上报告平均表现和失败率。
3. **CodeContests 不是生产项目。** 其 solution 相互独立、依赖少、I/O 统一，无法覆盖版本兼容、跨模块状态和框架生命周期等工程约束。
4. **测试验收可能泄露评估信息。** 当前同一测试集同时承担回滚和最终验证。更严格的设置应使用 validation tests 选择候选，再在不可见 held-out tests 上报告结果。
5. **完整组合尚未物化。** CodeContests 的 5.13% 是文件互斥条件下的保守 token 核算；各候选当前分别拥有自己的 `common.py`，联合部署前还需要进行模块命名或组合，并重新运行完整测试。
6. **仅报告单次模型运行。** temperature 虽为 0，但远端 API 仍可能存在非确定性；后续应进行多次独立运行并报告均值、方差与成本。
7. **MDL 暂未纳入。** 本轮没有统一且稳定的 logprob 参照模型，因此只报告可复现的 Python token 结果。

## 7 结论

本实验支持以下结论：

1. Signal 在两种数据条件下都获得了高于 Baseline A 的完整池有效压缩；真实 Libcloud 上为 9.88% vs 0.05%，受控 CodeContests 上为 5.13% vs 3.81%。
2. Signal 的核心优势是局部性：它能够在异质文件池中发现稀疏的高价值实现家族，并将风险和固定开销限制在局部候选内。
3. 多信号召回提升了候选覆盖，LLM 判定门减少了表面相似导致的错误抽取，行为测试和收益门则阻止失败或负收益结果进入最终代码池。
4. 负收益候选客观存在，不能隐藏或简单平均。把它们回滚是可执行的部署策略，但必须对所有方法使用同一规则，并同时披露未筛选结果。
5. 目前最稳妥的论断是：**Signal 在目标真实代码场景中提供了显著优势，并在受控数据上得到方向一致的补充证据；更广泛的普遍性仍需预注册、多仓库、独立测试集和重复运行验证。**
