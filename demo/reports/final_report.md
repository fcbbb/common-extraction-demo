# 代码共性组件抽取：端到端抽取与先发现再抽取两种流水线的对比研究

> 数据：CodeContests 聚类数据（10 簇 × 30 题）与 Scrapy 中间件/管道代码切片（24 文件，pytest 验证）
> 模型：DeepSeek V4 Flash API（temperature=0）
> 指标：功能等价（file/test pass rate）、MDL 压缩率、token 压缩率、API coverage、改写冲突率

---

## 1 任务设定

### 1.1 任务定义

给定一个由若干独立源代码文件组成的文件簇 `C = {f_1, ..., f_n}`，要求抽取出一份共享组件库 `common.py`，并把簇内文件改写为引用该库的成员文件，使得：

1. **功能等价**：改写后的成员文件与原始文件在同一测试集上表现一致；
2. **压缩收益**：`common.py + 改写后成员文件` 的代码规模/信息量低于原始文件包，且压缩必须建立在真实复用（改写文件实际调用库接口）之上。

任务输入输出均为代码，评估以测试集（prompt 外部）作为功能等价的裁判。

### 1.2 输入约束

LLM 的 prompt 中只暴露中性化的源码文件：

```json
{"file_id": "file_000.py", "source_code": "..."}
```

以下字段一律不进入 prompt：题名 `name`（可能泄露题型）、题面 `description`（直接泄露算法语义）、算法摘要 `short_description`、难度 `difficulty`、以及全部测试用例。测试只用于 prompt 外部验证。对框架代码数据集，同样只暴露源码文件本身。

### 1.3 评估指标

按重要性排序，功能等价是硬约束，压缩收益只有在功能等价的改写上才计入：

| 指标 | 定义 | 计算对象 |
|---|---|---|
| file pass rate | 改写文件与原始文件在同一测试集上全部通过的占比 | 原始 solution vs 改写文件，同一测试集 |
| test pass rate | 通过的测试用例占比 | 同上 |
| MDL 压缩率 | `1 - NLL(after) / NLL(before)`，before/after 用同一个参照 LM 计算 | `before` = 原文源码包；`after` = `common.py` + 改写文件（`common.py` 必须计入） |
| token 压缩率 | `1 - tokens(after) / tokens(before)` | 同上，用 tiktoken（gpt-4）计数，回退 python-tokenize |
| file API coverage | 至少调用一个 common API 的改写文件占比 | common.py 顶层 def/class 与改写文件 AST 调用 |
| API usage coverage | 被至少一个改写文件调用的 common API 占比 | 同上 |
| 冲突率 | LLM 自述 `call_mapping` 与 AST 实际调用不一致的比例 | mapping 声称未调用、声称调用不存在、实际调用未记录等 |

判定顺序：**先看 pass rate，再看压缩率**。功能不等价的压缩（例如删坏代码获得的体积下降）不计为正收益。

> **pass rate 上限说明**：matched 判定要求改写输出与原始输出一致，且原始文件自身需通过该用例（`returncode==0` 且不超时）。因此 pass rate 的上限是**原始文件自身在测试集上的通过率**——原始题解自带的 bug 或超时会直接计入改写文件的失败，pass rate 不可能达到 100%。抽样验证（簇 0、9）：原始文件自身全过率 80.0% / 93.3%，对应改写后 76.7% / 80.0%；两者之差才是改写真正引入的功能退化。

## 2 方法

两种 baseline 使用同一模型、同一 temperature（0）、同一回炉策略（JSON 解析失败或编译失败时追加错误信息重试一次），差异只在流水线组织方式。

### 2.1 Baseline-a：端到端一次性抽取

单次调用把整个文件簇的全部源码交给 LLM，要求它一次性完成三步：发现共享组件、写出 `common.py`、改写所有成员文件并附 `call_mapping`。

- 优点：流程最短、上下文完整、不依赖中间决策；
- 风险：发现与改写耦合在一次生成中，簇内混入异质文件时容易被"带偏"。

### 2.2 Baseline-b：先发现再抽取

两阶段流水线，把"发现"与"抽取"解耦：

- **Step 1（发现）**：单次调用只看簇内源码，输出子簇划分 `{sub_0: [成员文件], shared_concept, shared_interface, key_variations}` 与噪声文件清单。成员少于 2 个的子簇不进入下一步；噪声文件不抽取、原样保留。
- **Step 2（抽取）**：对每个有效子簇单独调用，输入子簇的共享概念、候选接口、关键差异与成员源码，输出与该子簇对应的 `common.py` 与成员改写。

- 优点：子簇内文件同质度高，抽取阶段的上下文更聚焦；
- 风险：发现阶段的划分与接口猜测错误会直接传导到抽取阶段。

### 2.3 输出约束

两种方法均要求：不引入第三方依赖、不改变输入输出行为、保留每个文件的 stdin/stdout 主流程（框架数据为保留原模块语义）、`common.py` 只放可复用 helper 与必要标准库 import、输出必须为可解析 JSON。

## 3 实验设置

### 3.1 数据集

**数据集一：CodeContests 聚类数据。** 10 个算法主题簇，每簇 30 道题的 `solution` 源码，共 300 个文件、约 3.0 万个测试用例（public + private + generated）。测试模式为 stdin/stdout：改写文件与原始 solution 在同一测试集上运行，按空白归一化后比较输出。

**数据集二：Scrapy 中间件/管道代码切片。** 单一簇，24 个非 `__init__` 源码文件（下载中间件 12、爬虫中间件 6、管道 2、`MiddlewareManager` 框架 1 等），共 4,341 行；配套 30 个上游 pytest 测试文件、512 个测试函数（与 scrapy commit `3c6a62db` 逐字节一致）。测试模式为 pytest：每个测试用例在原始布局与改写布局中各跑一次，结果一致（pass/fail/error/skip）记为通过。文件规模、依赖关系（`scrapy.middleware` 模块内部互相引用）与真实框架的类继承/回调机制，使其与算法题代码在"共性组件形态"上有本质差异：前者是函数级 helper，后者是类继承与框架回调。

### 3.2 模型

DeepSeek V4 Flash API，temperature=0，单次采样，无多样本 rerank。call log 记录每次调用的 prompt/response 与 usage。

### 3.3 参照 LM 与 MDL

DeepSeek API 不提供可用的 logprobs，MDL 使用本地开源 coder LM 作为固定参照：`Qwen3.8-27B-Q4_K_M.gguf`（llama-cpp-python，n_ctx=4096，n_gpu_layers=-1，n_batch=256）。参照 LM 只要求 before/after 同模型可比。

### 3.4 压缩率口径

- **Baseline-a**：`before` = 整簇原文，`after` = `common.py` + 整簇改写文件，两侧同范围。
- **Baseline-b**：`before` 与 `after` 均按**子簇成员范围**统计（与测试范围一致，是与 Baseline-a 的簇级口径同类可比的"单元内"比较）；另设"簇级重组口径"作为参考：`before` = 整簇原文，`after` = Σ（各子簇 `common.py` + 改写成员）+ 未改写噪声文件。
- 本报告正文一律采用成员范围口径；簇级重组数字仅在分析中作为参考。token 计数使用 tiktoken（gpt-4），回退 python-tokenize；MDL 以同一参照 LM 对 before/after 计算 NLL。

## 5 分析

### 5.1 方法对比：端到端 vs 先发现再抽取（RQ1）

在 CodeContests 上，Baseline-a 在**功能保持与压缩收益两个维度上都占优**：file pass 88.0% vs 81.8%，token 压缩 23.3% vs -3.9%（成员口径）/ 5.7%（簇级重组口径均值），MDL 压缩 0.310 vs -0.0231（成员口径均值）。

Baseline-b 的真正代价在于：发现阶段把簇切成子簇后，抽取阶段的比较对象变小（子簇内同质文件），LLM 倾向于为每个子簇**新写一份库并把成员文件重写为库的调用方**，而不是在整簇尺度上消除重复——结果是"库 + 改写文件"的总量与原文相当甚至更大（64 个子簇中 token 口径仅 33 个、MDL 口径仅 31 个获得正压缩，均值 -3.9% / -0.0231）。同时发现阶段的划分错误会直接造成功能退化（见 5.3）。

### 5.2 压缩的真实性：什么情况下压缩是真实收益（RQ2）

按计划口径"pass 高 + 压缩高"才是真实收益：

- **Baseline-a 的压缩真实且保守**：10 簇平均 file API 覆盖 91.3%、usage 覆盖 80.3%，即压缩主要来自改写文件实际调用库接口；MDL 压缩（0.310）高于 token 压缩（23.3%），说明改写后代码在参照 LM 下更"可预测"（结构更规整），这是真实去重的信号。各簇压缩差异大（token 9.7%–61.3%），与簇内同质程度相关。
- **Baseline-b 的压缩两极分化**：少数大子簇取得真实收益（1/sub_0，11 文件，MDL 0.812 / token +63.1% 且 100% 通过；8/sub_1，MDL 0.430 / token +38.0% 且 100% 通过），但 31 个子簇 token 口径改写后**变大**（5/sub_6 甚至 -80.7% 且 100% 通过——改写保留了功能但代码膨胀近一倍），MDL 口径 33 个子簇为负（均值 -0.0231）。这支持"先发现再抽取"在高同质子簇上有效、在一般子簇上退化为"复制进库而不删原文"的判断。另有功能退化换压缩的案例（2/sub_5：token +37.1%、MDL +0.583，0% 通过）。
- 冲突率 200% 的两个子簇（5/sub_4、7/sub_3）中，mapping 声称与 AST 调用相互错位（`claimed_missing_api` 与 `called_but_not_mapped` 并存，声称名带 `common.` 前缀而实际调用不带），这两处的压缩数字不能采信。

### 5.3 发现质量：子簇划分是收益的前提（RQ3）

- 64 个有效子簇全部被模型判定有效（valid = discovered），说明"从源码判断共享组件"这一步在算法题代码上总体可行；
- 但发现阶段的错误会以两种方式传导：**接口猜错**（9/sub_0，11 文件仅 18.2% 通过；0/sub_0，25.0%）和**成员分错**（cluster 1 的 file_003 被分入两个子簇；Scrapy 侧 file_008 同样被分入 sub_1 与 sub_2 两个子簇；2/sub_5 的 0% 通过）；
- 59 个文件（19.7%）被判为噪声而不改写：这些文件没有功能风险，但也意味着 baseline-b 的端到端压缩收益上限天然低于 baseline-a；
- 子簇规模与通过率无单调关系：11 文件的大子簇 1/sub_0 100% 通过，而 2 文件的小子簇 2/sub_5 0% 通过——失败主要取决于共享接口是否真实存在，而非规模。

### 5.4 数据泛化：算法题 vs 真实框架代码（RQ4）

两数据集的对比揭示共性组件形态对方法有效性的决定性影响：

- **算法题代码（CodeContests）**：共性是函数级 helper（例如树的遍历、数学工具），提取与替换是"机械的"调用改写，Baseline-a 能在 88% 文件上保持功能并获得 23.3% 的压缩。
- **框架代码（Scrapy）**：共性是类继承、框架回调与模块间引用（中间件基类、manager 机制）。Baseline-a 以"几乎不改写"的方式保全了功能（100% 通过、token +0.2%、MDL -0.0335），说明端到端模型在真实框架代码上选择了保守策略，但改写几乎无压缩收益；Baseline-b 功能保持尚可（file pass 85.0%、test pass 99.7%），压缩全面为负（token -2.4%、MDL -0.1154、冲突 33.3%）。
- 一个例外值得注意：Scrapy sub_4（6 文件，100% 通过，token 压缩 +0.1%）将 `BaseSpiderMiddleware` 基类收进 common.py 并改写全部 import，**是框架代码上真实复用的成功案例**，但被冲突指标误报为 100%——因为 usage 检测器只统计函数调用与类实例化，不识别基类继承与 import 级复用（详见 5.5）。

结论：先发现再抽取的激进策略只在"共性可被显式枚举"的代码上成立；对以继承/回调为共性的真实框架代码，需要把"基类继承"纳入复用检测与冲突判定，否则评估与抽取都会失真。

### 5.5 冲突率：LLM 自述 mapping 的可信度（RQ5）

冲突率从 CodeContests-a（7.7%）、CodeContests-b（11.2%）到 Scrapy-b（33.3%）、Scrapy-a（62.9%）逐级升高——算法题代码上 mapping 总体可信，框架代码上两种方法的 mapping 都高度失真，且主要不是改写质量问题，两个机制：

1. **自述失真 + 检测器盲区叠加**：`claimed_missing_api` 不区分"幻觉声称"与"检测器不认识的用法"。Scrapy-a 的 mapping 声称 35 项调用、AST 实际仅 13 处，22 项冲突全部指向 `Self`：改写文件大量使用 `-> Self` 返回类型注解配合 common.py 的 `from typing import Self`，属真实复用，但检测器只识别顶层 def/class 名，import 名一律判为"声称的 API 不存在"。Scrapy-b 的 sub_0（6/9）声称调用 `PerSpiderSettingMiddleware` 的类方法（`from_crawler`、`process_request` 等），类本身在 API 清单内、类方法不在，同样被误判。
2. **继承式复用不在检测器视野内**：Scrapy-b sub_4 的 6 个文件全部 `from common import BaseSpiderMiddleware` 并以基类继承方式使用，检测器识别为 0 次调用、冲突 100%，但该改写实际真实有效（100% 通过）。当前冲突指标在继承式复用上会产生假阳性。

结论：冲突率作为软指标，能有效暴露"mapping 自述与实际行为脱节"的高风险改写（200% 的案例、Scrapy-a 的高冲突），但在真实复用的边界形态（import 名、类方法、基类继承）上会产生大面积假阳性，需要配合 usage 检测能力的扩展，不能单独作为改写可信度的裁判。
